# HTTP and data

## Contract

Routes hang off `/api/v1/` and end with a trailing slash, matching `config/api_urls.py`. Public field names are whatever the current serializer emits. Rename a field only when the frontend caller changes in the same work.

Do not invent a `{ "status": "success", "data": ... }` envelope. This API returns DRF's default body: the serializer data, or `{ "detail": ... }` / field errors. The token pair is `{ "access", "refresh" }`.

Status codes stay literal:

| Code | When |
| --- | --- |
| 200 | Read or update that returns a body |
| 201 | Create |
| 204 | Delete with no body |
| 400 | Serializer validation, including a filled honeypot |
| 401 | Missing or invalid JWT |
| 403 | Authenticated but not staff, where `IsAdminUser` applies |
| 404 | Unknown slug, token, or id |
| 429 | Throttle |

Do not return 200 for a rejected write. Do not put a stack trace in the response. `DEBUG` must not become a way to leak tracebacks to the public site.

## Lists

`PAGE_SIZE` is 20 with `PageNumberPagination`. A new list uses that paginator. Do not return an unbounded `objects.all()` from a public list once the table can grow (posts, projects, comments, events, subscribers).

Filter and search through the backends already in `REST_FRAMEWORK` (`DjangoFilterBackend`, `SearchFilter`, `OrderingFilter`) when the sibling viewset does.

## Queries

List serializers stay smaller than detail serializers, as `PostListSerializer` versus `PostSerializer`. Use `select_related` and `prefetch_related` for relations the serializer touches. `APPROVED_COMMENTS_PREFETCH` is the pattern for a filtered relation. Do not prefetch every relation on a list "to be safe."

Public querysets hide drafts and unapproved rows. Admin querysets on the same model may include them. Do not reuse the public queryset for the admin inbox or the admin queryset for the public list.

## Writes

- Slugs are stable. A public `by-slug` action is a read.
- Status fields that already move through a method (publish, approve, verify) stay on that method. Do not add a free-form `status` that any client can set to any string.
- Unique constraints (subscriber email, slug) are the duplicate guard. A replay of the same subscribe should not create a second row or send a second verify mail if the address is already pending or active. Match the existing service behaviour rather than inventing an idempotency table.
- Side effects after a successful save: notifications and mail go through `NotificationService` or `NewsletterService`. A failed send is logged. It does not pretend the row was not saved if the row commit already happened.

## Migrations

One change, one migration, generated by Django. Do not edit a migration that has already been applied in a shared environment. Expanding a column is a nullable add, then a backfill, then a constraint, when the table already has rows. Do not drop a column the frontend still reads in the same release.

## Health

`GET /api/v1/` returns `{ "status": "ok" }` for probes. Do not hang that view on the database, Redis, or email. Readiness for those dependencies belongs on a separate check if one is added.
